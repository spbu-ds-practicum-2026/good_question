# Магазин «Семёрочка»

## Запуск демостенда

Установите Docker с Compose v2. Из корня репозитория выполните:

```bash
docker compose up --build -d --wait
docker compose ps -a
```

Gateway открыт на `http://127.0.0.1:8000`, интерфейс — на `http://127.0.0.1:8080`.
Catalog, Order, Payment Mock, RabbitMQ и три экземпляра PostgreSQL доступны внутри сети Compose.
При первом запуске Compose дожидается готовности БД и брокера,
запускает миграции Order и Payment, подготавливает очереди и создаёт пять товаров
с начальным остатком по 25 единиц. Служебные контейнеры миграций, настройки
RabbitMQ и наполнения базы после выполнения завершаются с кодом 0.

Порты, таймаут Gateway и ключ подписи можно переопределить в `.env`
по образцу `.env.example`. Учётные данные из Compose предназначены для этого
локального стенда. `docker compose down` останавливает стенд. Данные PostgreSQL
и RabbitMQ сохраняются в именованных томах между запусками.

### JWT

Gateway проверяет подпись HS256 и срок действия токена. Для бизнес-маршрутов
поддерживаются роли `user` и `admin`. Только администратор может менять каталог,
устанавливать начальный остаток и менять статус заказа. Клиент передаёт
`Authorization: Bearer <JWT>`. Gateway формирует доверенные заголовки
`X-User-Id` и `X-User-Role` из токена.

```bash
docker compose exec -T gateway python -m gateway.tokens user
docker compose exec -T gateway python -m gateway.tokens admin
```

Обе команды выпускают JWT на 24 часа. Вставьте нужный токен в форму входа
на странице или передайте его в HTTP-запросе.

### Что показать на демо

Сценариям нужны Bash, curl и jq. Запускайте по одной команде после старта стенда.

| Команда | Что проверяет |
| --- | --- |
| `bash scripts/demo.sh auth` | Каталог возвращает `401` без JWT и `200` с JWT. Пользователь получает `403` при создании товара, администратор получает `201`. Order подтверждает начальный остаток товара. |
| `bash scripts/demo.sh catalog-outage` | При остановке Catalog запрос каталога возвращает JSON с `503 upstream_unavailable`, история заказов отвечает `200`. После запуска Catalog снова отвечает `200`. |
| `bash scripts/demo.sh broker-outage` | При остановке RabbitMQ заказ остаётся `PENDING_PAYMENT`, а попытка публикации фиксируется в Outbox. После запуска брокера событие публикуется и заказ переходит в `PAID`. Повтор результата оплаты с тем же `eventId` проходит через брокер и оставляет статус, резерв, историю и уведомления прежними. |

Gateway возвращает `504 upstream_timeout`, когда проксируемый запрос превышает
выделенное время (по умолчанию 6 секунд). Формат ошибок — `{"error":{"code":"…","message":"…"}}`.

Для ручного показа остановки и восстановления используйте `docker compose stop catalog`
и `docker compose start --wait catalog` или те же команды с именем `rabbitmq`.
Сценарий оплаты выполняется через API. В текущей версии интерфейс хранит корзину
в браузере и отправляет другую схему оформления.

### Контракт RabbitMQ

Exchange `payments.events` имеет тип `direct`. Все очереди и обменники сохраняются
между перезапусками брокера. Отклонённые сообщения попадают в очередь `payments.dead`.

| Очередь | Потребитель | Ключи маршрутизации |
| --- | --- | --- |
| `payments.commands` | Payment Mock | `payment.requested`, `payment.refund.requested` |
| `orders.payments` | Order Service | `payment.completed`, `payment.failed` |

Общий формат сообщения задаётся моделью `Event` в `order_payment/messaging.py`.
В JSON передаются `eventId` (UUID, совпадает с AMQP `message_id`),
`eventType` (совпадает с ключом маршрутизации), `occurredAt` и `data`
с полями `orderId`, `amount` (копейки), `currency` и `paymentMode`.
Relay помечает запись Outbox опубликованной после подтверждения RabbitMQ.
Потребитель подтверждает доставку после коммита транзакции с бизнес-эффектом
и записью `eventId` в `processed_events`.

## Структура
- `services/` — код сервисов (любой язык)
- `docs/` — ТР (техрешение), архитектура, UML
- `.github/` — шаблоны задач и PR

## Как работать
1. Создайте ветку от `main`.
2. Пишите код в `services/<service>/`.
3. Если меняете архитектуру — обновляйте `docs/tr.md`.
4. Делайте PR в `main` — используйте шаблон PR.

## Требования к PR (минимум)
- Понятное описание
- Обновлённые docs при архитектурных изменениях
- Запускается локально (опишите в `services/<service>/README.md`)
